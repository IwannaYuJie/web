## 先说结论

7 月 16 日，Google Cloud 宣布在 Gemini Enterprise Agent Platform 中原生接入 **Parallel Web Search**。

它看上去只是“Gemini 又多了一个联网搜索服务”，但真正重要的不是多一个搜索框，而是 Google 把搜索源选择、实时网页数据、精确引用、数据缓存和多模型编排都放进了企业 Agent 平台。

这说明 2026 年的 Agent 竞争，已经不只是比模型本身有多聪明。一个 Agent 要替公司做尽调、查合规、更新商品目录或分析实时新闻，必须回答三个更现实的问题：

1. 信息是不是最新的？
2. 结论能不能追到原始来源？
3. 搜索结果能不能被系统继续处理，而不只停留在聊天回答里？

模型负责推理，搜索负责连接现实。两者之间的 Grounding（事实锚定），正在变成企业 Agent 的基础设施。

## Google 这次具体加了什么

Parallel Web Search 现在可以在 Gemini API 中调用，也能在 Agent Studio 中选择，并通过 Google Cloud Marketplace 订阅，费用合并进现有 Google Cloud 账单。

它提供的核心能力包括：

- 使用面向 Agent 工作负载设计的网页索引；
- 返回结构化、适合大模型处理的实时搜索结果；
- 让 Gemini 分解复杂问题、筛选资料并生成带精确引用的回答；
- 支持开发者提取、长期缓存和二次处理网页数据；
- 搜索结果可以继续交给其他大模型或子 Agent；
- 对敏感工作负载提供零数据保留（ZDR）选项。

最后三点尤其值得注意。普通聊天产品里的联网搜索，目标是“这次回答有资料”；企业系统需要的是“这些资料能进入我的数据管道，能复用、能审计、能交给别的模型继续干活”。

## 什么是 Grounding，它和普通联网有什么区别

Grounding 可以理解成：在模型生成答案前，先把它的推理锚定到可验证的外部事实上。

一个完整的 Web Grounding 链路通常是：

1. Agent 理解问题并拆成若干检索任务；
2. 搜索服务获取最新网页结果；
3. 系统抽取正文、时间、来源和链接；
4. 模型对多来源进行比较与归纳；
5. 输出结论，同时保留引用关系；
6. 应用根据风险决定自动执行还是交给人审核。

普通“让模型上网搜一下”往往只关注第 2 和第 5 步。生产级 Grounding 则要处理来源质量、时效性、授权、缓存、去重、引用映射和失败回退。

所以它不是一个按钮，而是一条数据工程链路。

## 为什么模型越强，反而越需要搜索

大模型的内部知识来自训练数据，天然存在截止时间。即便模型对历史知识理解很好，也不可能凭参数知道刚刚更新的价格、法规、公司公告或库存。

更麻烦的是，强模型能把不完整信息组织得非常像真的。回答越流畅，用户越容易忽略事实已经过期。

Agent 和普通聊天又不一样。聊天答错，用户可能只是看到一段错误文字；Agent 如果根据错误信息更新数据库、触发付款、筛选客户或提交合规结论，错误会直接变成动作。

因此，Agent 自主性越高，对实时、可引用数据的要求就越高。**能行动的 AI，必须比只聊天的 AI 更会证明自己。**

## Parallel 的价值不只是“另一个搜索引擎”

Google 原本就有自己的搜索能力，这次仍引入第三方 Grounding 提供商，释放了一个很强的信号：企业 Agent 平台会逐渐走向多数据源、多模型和可替换组件。

不同搜索基础设施可能在覆盖范围、刷新速度、结构化程度、许可条款、缓存能力和地区合规上各有优势。企业不一定愿意把所有 Agent 都绑在同一个搜索源上。

Parallel 这次强调的特点是面向 Agent 的结构化结果，以及更灵活的程序化使用：开发者可以规模化调用、抽取和缓存网页数据，还能把结果交给其他模型继续处理。

这会带来一种更开放的架构：

| 层级 | 可以替换什么 |
| --- | --- |
| 检索层 | Google Search、Parallel、企业自建搜索 |
| 推理层 | Gemini 或其他任务型模型 |
| 编排层 | 主 Agent、子 Agent、工作流引擎 |
| 数据层 | 内部知识库、缓存、审计记录 |
| 执行层 | CRM、工单、数据库、业务 API |

模型不再包办一切，而是成为系统中的一个推理节点。

## Web Grounding 和企业 RAG，不是谁替代谁

很多人看到联网搜索，会问企业内部 RAG 是不是没用了。其实两者解决的是不同问题。

- **Web Grounding** 负责公共、实时、外部世界：新闻、官网、法规、市场与公开数据库；
- **企业 RAG** 负责私有、受权限控制、组织内部的信息：合同、产品文档、客户记录、操作手册和历史决策。

真正有价值的企业 Agent 往往需要把两者合起来。

例如做供应商风险评估：内部 RAG 提供合同、付款和交付记录；Web Grounding 提供公司公告、监管处罚和最新新闻；模型负责比对冲突并生成风险说明；高风险结论再交给人审批。

如果只查外网，Agent 不懂公司自身关系；如果只查内网，它又看不到世界已经变化。

## 最先受益的三类场景

### 1. 持续更新的数据补全

大型商品目录、供应商库和客户库经常缺字段。Agent 可以定期查找公开资料，提取可验证信息，保存来源和更新时间，再把候选更新交给规则或人工确认。

### 2. 合规与尽调

Agent 可以把内部文件与公开监管网站、公司公告和新闻交叉核对，持续检查高风险变化。这里最重要的不是生成一段总结，而是每个风险点都能回到原始证据。

### 3. 多 Agent 研究

一个主 Agent 拆分问题，多个子 Agent 分别查市场、技术、公司和监管信息，再由主 Agent 汇总。Parallel 的搜索结果可以交给不同模型继续处理，让团队不必把所有任务锁在同一个模型里。

## 别把“有引用”误当成“绝对正确”

引用能提高可验证性，但不会自动消除错误。

常见问题包括：

- 搜到的是转载，不是原始来源；
- 页面很新，但内容本身没有证据；
- 引用链接存在，却没有真正支持结论；
- 不同地区和时间版本的规则被混在一起；
- 缓存数据过期，系统仍把它当实时结果；
- 恶意网页用 Prompt Injection 诱导 Agent 偏离任务。

因此生产系统至少要保存查询词、来源 URL、抓取时间、关键证据片段、模型结论和最终动作。高风险场景还要设置来源白名单、交叉验证和人工审批。

Grounding 的目标不是让模型“永远正确”，而是让错误更容易被发现、解释和纠正。

## 我看到的下一场竞争

过去两年，厂商主要争模型入口；接下来，它们会争 Agent 接触现实世界的入口。

谁拥有更新更快、许可更清晰、结构更适合机器处理的数据，谁就能让 Agent 做更多实时工作。模型可以更换，数据管道、权限体系、缓存和审计一旦接进企业流程，黏性反而更强。

因此，搜索不再只是面向人的“十条蓝色链接”，而会变成面向 Agent 的实时数据 API。网页也不只是让人阅读的页面，而会成为机器不断抽取、验证和行动的外部状态。

## 最后

Google 接入 Parallel Web Search，表面上是在扩充 Gemini Enterprise Agent Platform 的搜索选择，背后却在说明一个更大的变化：

> Agent 的能力上限，不只由模型决定，也由它能接触什么数据、怎样证明结论、以及能否把证据安全地带进下一步行动决定。

模型负责想，搜索负责看，权限负责管，审计负责追。把这四件事接好，Agent 才能从“会联网聊天”走到“能在现实世界里可靠做事”。🐱
