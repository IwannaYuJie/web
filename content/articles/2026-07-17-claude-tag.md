## 先说结论

Anthropic 在 6 月 23 日发布了 **Claude Tag**。它先从 Slack 开始：管理员把 Claude 接入指定频道、工具、数据和代码库，团队成员就可以直接 `@Claude` 分配任务。

乍一看，这只是把 AI 助手塞进群聊。但 Claude Tag 真正改变的是 Agent 的使用单位：

- 以前是“一个人和一个 AI 的私聊”；
- 现在是“一个团队和一个共享 Agent 的协作”；
- 以前每次都要重新交代背景；
- 现在 Agent 会在授权范围内持续积累频道上下文；
- 以前 AI 等人提问；
- 现在它可以主动提醒、异步工作，甚至把任务排到未来继续做。

这条路线如果跑通，AI 就不再只是个人效率工具，而会成为组织工作流里的一个角色。

可一旦它变成“团队成员”，麻烦也跟着来了：它该知道多少？能代表谁做决定？犯错算谁的？记忆又该保存多久？这些问题比模型能不能写代码难多了。

## Claude Tag 能做什么

Claude Tag 目前面向 Claude Enterprise 和 Team 客户提供 Beta，使用的是 Opus 4.8。根据 Anthropic 的介绍，它有四个明显特点。

### 1. 它是“多人共享”的

同一个 Slack 频道里，大家看到的是同一个 Claude。任何人都能看到它正在做什么，也能接着同事之前的对话继续推进。

这和普通聊天助手最大的区别，是工作不再锁在某个人的私聊记录里。需求、讨论、任务过程和交付结果都留在团队公共上下文中。

### 2. 它会逐渐积累上下文

Claude 可以从被授权的频道和数据源中建立记忆，减少团队反复解释项目背景。管理员可以把不同用途的 Claude 隔离开，例如销售 Claude 和工程 Claude 使用不同频道、工具和记忆范围。

Anthropic 还特别说明，它不会把私密频道内容带到公共场景。这个设计很关键：组织记忆必须和权限边界一起增长，不能因为 AI “记得更多”就顺手把更多内容泄露出去。

### 3. 它可以主动跟进

开启 ambient 行为后，Claude 会主动标记相关信息、提醒沉默太久的任务、追踪没有解决的线程。

这让它从“问一句答一句”的机器人，变成一个可能主动找你的协作者。对项目推进很有用，对通知焦虑也很危险。一个过度积极的 Agent，完全可能变成群里最吵的那个人。

### 4. 它能异步工作

团队把任务交给 Claude 后，可以先去做别的事。它能在后台工作，也能为自己安排未来任务，持续数小时甚至数天推进一个项目。

这类能力特别适合长链路工作：汇总跨频道信息、追踪指标、分析支持工单、调查 Bug、准备周报，或者等待外部条件满足后继续执行。

## 从聊天助手到“组织里的共享状态”

个人 AI 最常见的问题，是上下文被困在个人账户里。

产品经理让 AI 整理需求，工程师又重新解释一遍；工程师排查完故障，运营再从头描述；某个员工离开团队，他和 AI 之间积累的工作方法也一起消失。

Claude Tag 想解决的不是单次回答质量，而是让 Agent 成为一种 **共享状态**：

| 个人助手 | 团队 Agent |
| --- | --- |
| 上下文属于个人 | 上下文属于授权频道 |
| 输出需要复制给同事 | 过程与结果直接留在团队空间 |
| 每个人分别教一遍 | 团队共同修正和沉淀 |
| 任务以对话结束为终点 | 任务可以异步持续推进 |

这种变化非常像早期文档从本地文件转向在线协作：价值不只是“编辑器更强”，而是大家终于围绕同一份状态工作。

## Anthropic 的 65% 代码数据该怎么看

Anthropic 称，目前其产品团队 65% 的代码由内部版 Claude Tag 创建。这个数字很吸睛，但别急着把它理解成“65% 的工程师已经被替代”。

“代码由 AI 创建”可能包含脚手架、测试、迁移、重构、文档和重复性改动，也不等于这些代码没有人工提出需求、评审、测试和负责上线。

更值得关注的是工作方式：Anthropic 的团队已经大量使用并行 Claude，把不同任务分给多个 Agent，再由人类决定方向和验收结果。

所以 65% 更像一个产品使用强度信号，而不是就业替代率。它说明 AI 生成代码在某些团队里已从偶尔帮忙，变成日常生产链路的一部分。

## 真正难的是权限，不是接入 Slack

把 Bot 加进 Slack 很简单，让它安全地做事才难。

Claude Tag 提供了频道级身份隔离、工具权限、组织与频道 Token 预算，以及完整操作日志。管理员还能看到每个任务是谁发起的。

这些能力背后对应四个生产问题：

1. **最小权限**：一个做周报的 Agent 没必要拥有部署生产环境的权限；
2. **上下文隔离**：销售、财务、工程和人事不能共享同一份记忆池；
3. **成本控制**：长期异步任务可能持续消耗 Token，必须有预算和停止条件；
4. **责任追踪**：Agent 做了什么、谁要求它做、谁批准了结果，都要留痕。

团队 Agent 的权限最好像新员工入职一样逐步开放：先读公共资料，再读项目数据；先生成建议，再允许提交草稿；等稳定后才考虑执行可回滚动作。

一上来就把代码库、客户资料和生产工具全部接进去，省下来的配置时间，迟早会在事故复盘里加倍还回去。

## 哪些任务最适合先交给它

Claude Tag 最适合那些跨多人、跨频道、信息分散，但最终动作风险不高的任务。

例如：

- 汇总本周各项目频道的进展，生成周报草稿；
- 追踪某个 Bug 的讨论、日志和修复状态；
- 归纳客户反馈，按主题整理成产品问题；
- 从指标、工单和讨论中发现异常线索；
- 给会议准备背景资料和未决事项；
- 检查一个任务是否长时间没人跟进。

不建议最先交出去的，是直接付款、自动删除数据、无人审核发布、修改生产权限等高风险动作。Agent 可以准备材料、提出方案、生成变更，但关键提交仍应经过人类确认。

## 它也可能制造新的组织问题

### 记忆不一定等于真相

频道里有很多临时讨论、过时决定和未经确认的观点。Agent 如果把它们都当成稳定知识，记得越多，反而可能错得越自信。

团队需要明确哪些是正式文档，哪些只是讨论；关键决策最好仍落到可版本化的文档，而不是只躺在聊天记录里。

### 主动性不一定等于生产力

Agent 可以主动提醒，不代表每件事都值得提醒。最好为它定义触发条件、安静时段、升级规则和通知频率，避免把团队注意力切成碎片。

### 共享 Agent 也会放大错误

个人助手答错，影响一个人；团队 Agent 在公共频道给出错误结论，可能让所有人沿着同一个错误方向行动。因此共享 Agent 更需要来源、可验证产物和人工复核。

## 我的判断：AI 会先成为“组织角色”，再谈替代岗位

Claude Tag 最有意思的地方，是它没有试图再造一个独立工作台，而是进入团队已经在用的 Slack。

这意味着 Agent 产品的竞争焦点正在改变：谁能接入更多真实上下文，谁能在权限内持续工作，谁能把结果留在团队流程里，谁就更接近生产环境。

未来公司里可能出现很多按职责划分的 Agent：工程频道里的排障 Agent、销售频道里的客户研究 Agent、运营频道里的数据巡检 Agent。它们不一定对应一个完整岗位，更像一组被权限、记忆和流程约束的数字角色。

## 最后

Claude Tag 表面上是“在 Slack 里 @ 一下 Claude”，实际上是在回答一个更大的问题：

> 当 AI 不再只服务一个人，而是参与整个团队的工作时，组织该怎样给它上下文、权限、预算和责任边界？

能不能写出漂亮回复，已经不是最难的部分。能不能在几个月的真实协作里，持续有用、不乱说、不越权、出了问题能追查，这才是团队 Agent 的成人礼。🐱
